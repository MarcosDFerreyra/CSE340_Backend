Let's start with the hashing itself. I see you're doing:

COACH: Totally fine to say "I don't know" — and honestly, your instinct about why we do this (never storing the actual password) is spot on. Let's clear up the salt part, since your mental model is close but mixed up with something else.

Here's what's actually happening:
- Hashing takes your full password and runs it through a one-way math function that produces a fixed-length string (the hash). It's not "taking only part of the password" — it uses the whole password, but the output is scrambled in a way that can't be reversed back into the original.
- When someone logs in, you don't "un-hash" their input — you hash the password they typed again and compare the two hashes. If they match, the password was correct.
- The salt is a random string added to the password before hashing. Its job is to make sure that even if two users pick the exact same password, they end up with completely different hashes stored in the database. Without a salt, an attacker could pre-compute hashes for common passwords (a "rainbow table") and instantly crack any match they find in a leaked database. The salt breaks that shortcut.

So bcrypt.genSalt(10) generates that random salt, and the 10 is the "cost factor" — it controls how computationally expensive the hashing is (higher = slower to compute, which is intentional, to make brute-force attacks harder).

Now, back to my original question: why did you choose to call bcrypt.genSalt(10) as a separate step, instead of just writing bcrypt.hash(password, 10) (which would generate a random salt internally for you in one line)?

MARCOS: If I hadn't separated them, would it have been the same?

COACH: Good question — yes, functionally the result would be the same. bcrypt.hash(password, 10) handles both salt generation and hashing internally in one call, and produces an equally secure result as doing genSalt then hash separately. The two-step version is really only useful if you need access to the salt value itself for some other purpose (which is rare in normal use), or it's just a pattern some tutorials teach. Neither is more secure than the other.

So to be clear: your code isn't wrong, it's just slightly more verbose than it needs to be.

Here's the key idea: a bcrypt hash isn't just a random-looking string — it actually has a specific structure. It looks something like this:
$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy

Breaking that down:

- 10$ — the cost factor (matches your genSalt(10))
- The next 22 characters — the salt, embedded right in the string

When you later call bcrypt.compare(enteredPassword, storedHash), bcrypt automatically extracts that embedded salt, re-hashes the entered password with it, and checks if the result matches. That's why your single password_hash column is all you need — nothing insecure about it.
